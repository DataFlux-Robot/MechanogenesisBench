# Benchmark 架构

[English](ARCHITECTURE.md) | **简体中文**

MechanogenesisBench 是面向评测器的协议，而不是智能体或产品运行时。参与者接收公开任务视图
和指导等级，然后作为外部进程运行。参与者输出内容寻址的 MRS 包、候选制品、构造/实验
receipts 和资源声明。任务持有的评测器使用私有视图作出决策；benchmark 验证器再独立检查
哈希、谱系、预算、证据等级和晋级谓词。

```text
公开任务 + 指导
        |
        v
第三方智能体进程 ----------> 内容寻址的提交
                                  |
私有评测器包 ------------------->+----> 评测决策
                                        |
任务 + 提交 + 决策 -------------------->+----> 验证器 + 向量评分
```

## 信任边界

参与者及其声明的 receipts 均不受信任。任务包、私有评测器包和验证器由 benchmark 方持有。
当前 runner 只提供进程级隔离，因此适合开发和一致性测试，不适合对抗性或竞赛级执行。

任务身份与评测器身份相互独立。公开任务材料参与任务包摘要，私有评测材料参与评测器摘要。
一次完成的运行同时绑定二者，防止评测器后来发生变化却静默沿用旧结果。

## 规范检查

当前可执行切片检查：

- schema 与内容寻址的 MRS 对象；
- 跨代的进程和世界谱系；
- 构造 receipt 的精确整数物料闭合；
- 评测器与制品绑定；
- 证据等级上限；
- 向量资源预算；
- 接受标志与晋级谓词的精确一致；
- 递归赛道中的有界递归 credit 条件。

Lean 模块形式化部分有限协议蕴含，Python 负责运行时解析、任务执行与具体验证。两层必须一致，
但若没有独立证据，任何一层都不会断言物理模型忠实，或 receipt 对应真实发生的事件。

## 赛道与比较类别

- `fixed_engine`：研究/执行系统保持不变；
- `open_system`：系统可以合成中间语言/程序，并使用声明过的外部工具；
- `recursive_learner`：提交额外尝试一个有界、相连的后继代声明。

指导等级从 G1（较多任务分解和协议提示）到 G5（只给任务与访问权限）。只有任务、赛道、
指导等级、证据等级和预算向量完全一致时，结果才可比较。

## 向量评分

单一标量可能让速度掩盖物料浪费，也可能让仿真得分伪装成硬件证据。因此 benchmark 将能力、
鲁棒性、自主性、时间、货币成本、能耗、物料、人工干预和有界递归 credit 保留为不同坐标。
任何排行榜策略都应位于该验证内核之上，并明确声明其取舍。
